# Flutter Architecture

## Folder purpose
- `lib/screens/` — one file per screen, flat (only `authentication/` is a subfolder). No `widgets/` folder yet — reusable pieces live inline in screen files (e.g. `common_app_bar.dart` is the only extracted shared widget).
- `lib/models/` — plain Dart classes with `fromMap`/`toJson` for Firestore documents. No codegen.
- `lib/services/` — Firebase/business-logic wrappers, intended to be called from screens (currently only `cart_service.dart`, which is an **empty stub** — cart logic currently lives inline in `pet_details_screen.dart` instead).
- `lib/theme_service.dart` + `lib/theme_service_provider.dart` — app-wide theme state (see State management below).
- `lib/firebase_options.dart` — generated by `flutterfire configure`; don't hand-edit, regenerate instead.
- `assets/images/` — the only declared asset folder (see `pubspec.yaml` `flutter.assets`).

## Known stub files (empty, 0 bytes)
- `lib/models/cart_item.dart`
- `lib/services/cart_service.dart`
- `lib/screens/cart_screen.dart`

Cart is currently implemented ad hoc inside `pet_details_screen.dart` (writes directly to the `carts` Firestore collection — see [firebase.md](firebase.md)). If asked to build out cart functionality, these three files are the intended home for it — don't assume they already contain logic just because they exist.

## Widget conventions
- Every screen is a `StatefulWidget` — there are currently zero `StatelessWidget`s in `lib/screens/`. Follow this unless the screen has no local/mutable UI state at all.
- File naming: `snake_case.dart` matching the class name (`login_screen.dart` → `LoginScreen`).
- Class naming: PascalCase with a `Screen` suffix for full pages (`BuyerDashboardScreen`), no suffix convention yet for smaller shared widgets (`CommonAppBar`).
- Private State class: `_<WidgetName>State` (standard Flutter convention, followed consistently here).
- Screens currently build Firestore calls directly in `State` methods (no repository layer) — see `buyer_dashboard_screen.dart` and `pet_details_screen.dart` for the pattern. Match this unless you're deliberately introducing a service layer.

## State management
- **No external state package** (no Provider, Riverpod, Bloc, GetX). Do not add one without discussing with the user first — this is a deliberate-looking minimal setup, not an oversight.
- Pattern in use: `ChangeNotifier` (`ThemeService`) exposed through a hand-written `InheritedWidget` (`ThemeServiceProvider`), consumed via `ThemeServiceProvider.of(context)`.
- Screen-local state uses plain `setState` inside `StatefulWidget`s.
- If extending theme/global state: add fields/methods to `ThemeService` and call `notifyListeners()` — don't create a second provider mechanism.

## Navigation / routing
- **No routing package** (no `go_router`, `auto_route`). Uses Flutter's built-in named routes.
- Routes are declared as a flat map in `MaterialApp.routes` in `lib/main.dart` (`/login`, `/dashboard`). Screens not in that map are pushed directly via `Navigator.push(MaterialPageRoute(...))` (see `pet_details_screen.dart` for the pattern).
- When adding a new top-level screen reachable by name, add it to the `routes` map in `main.dart`; for screens only reached by pushing from another screen (e.g. detail pages), a direct `MaterialPageRoute` push is the existing convention — no need to register it.

## Themes
- All theme definitions live in `ThemeService.themes` (`lib/theme_service.dart`) — a static list of maps with `value`, `viewValue`, `primaryColor`, `accentColor`. Dark variants are `<value>-dark` strings, not separate entries.
- The active theme is persisted to Firestore at `users/{uid}.theme` (see [firebase.md](firebase.md)) and loaded on startup in `main()`.
- To add a theme: append to `ThemeService.themes`, following the existing color-int format (`0xffRRGGBB`).

## Localization
- **Not configured.** No `flutter_localizations`, no `intl`, no `l10n.yaml`, no `.arb` files. All strings are hardcoded English in the widget tree. If asked to add localization, this is a from-scratch setup, not an extension of existing infrastructure.

## build_runner / code generation
- **Not used.** No `build_runner`, `freezed`, `json_serializable`, or `.g.dart` files anywhere. Models are hand-written with manual `fromMap`/`toJson`. Don't assume generated code exists or needs regenerating.

## FVM (Flutter Version Management)
- **Not configured.** No `.fvmrc`, no `.fvm/` directory. The Flutter SDK/channel in use is whatever `flutter --version` resolves to on the developer's machine (see `.metadata` for the last-known Flutter revision this project was touched with: `5874a72aa4c779a02553007c47dacbefba2374dc`, stable channel).
- If the user asks to pin a Flutter version, that means introducing FVM fresh (`fvm install`, `fvm use`, commit `.fvmrc`) — there's no existing convention to follow.

## Assets
- Declared in `pubspec.yaml` under `flutter.assets` as a single folder: `assets/images/`. No per-file asset declarations, no font assets, no resolution-variant (`2.0x`/`3.0x`) folders in use.
- Adding a new image: drop it in `assets/images/`, no `pubspec.yaml` change needed since the whole folder is already declared.

## Common commands
- `flutter pub get` — install dependencies.
- `flutter run` (or `./dev.sh` from this folder — an interactive device picker that boots a simulator/emulator, waits for it, then runs).
- `flutter analyze` — static analysis (`analysis_options.yaml` uses `package:flutter_lints/flutter.yaml`).
- `flutter clean` — clear `build/`/`.dart_tool/` if you hit stale-build issues (see Troubleshooting in [deployment.md](deployment.md)).

See [firebase.md](firebase.md) for Firestore/Auth details, [deployment.md](deployment.md) for build/release, [testing.md](testing.md) for test conventions.
